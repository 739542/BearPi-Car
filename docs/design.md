# 需求、功能与非功能设计

## 项目目标和分期

让操作者从电脑调试两只车轮，逐步过渡到用手机无线驾驶，再让另一位成员加入离线语音控制。同一辆车可以在课堂上连续演示手动驾驶、动作编排和语音操作。前两部分已有实现，语音部分是下一阶段交付目标。

| 阶段 | 场景与需求 | 实现和验收状态 |
| --- | --- | --- |
| 1 底盘点动 | 确认左右轮及行进方向 | 单轮、前进、后退、原地转向；每次最多约半秒。小组已实车确认 M1 左、M2 右 |
| 2 电脑驾驶 | 从离散方向扩展到连续操控 | USB 串口控制台支持方向键、组合键弧线、鼠标圆形摇杆与 JSON 路线。实车反馈用于修正倒车转向 |
| 3 手机驾驶 | 双手分别控制油门和转向，松开即停 | 先由电脑通过 USB 转发，再由车端提供热点和网页。后者可脱离电脑行驶，主板单独供电 |
| 4 展示与驾驶反馈 | 支持两种动力模式和可重复的展示 | v11 已烧录、恢复停车并启动热点。双指输入、松手请求、动作中止和横竖屏已在浏览器模拟环境验证。新版视觉效果的手机实测独立记录 |
| 5 语音驾驶 | 用中文执行前进、后退、转弯、停车 | 模块到手，识别、指令映射、控制权切换和实车验收由接手成员完成 |

## 一次操作是怎样执行的

手机浏览器加载板内 HTML、CSS、JavaScript。左手给出带符号的油门，右手给出转向。board_transport.js 按两轴输入分配左右轮输出并修正倒车转向。驱动请求携带会话号和递增序号。wireless.c 核对请求后调用 CarSetWheels，motor_test.c 把每个轮子的符号转换成方向，把幅值转换成 PWM。板端使用普通 HTTP，手机加入小车的 2.4 GHz 热点即可打开网页。

电脑端通过 115200 波特率串口发送 AT 命令。AT+CAR=1 到 6 依次执行左轮、右轮、后退、前进、左转、右转点动。AT+DRIVE 用于持续方向输入，AT+JOY 用四个十进制数字编码左右轮，各两位，30 为中点。两个车轮速度不同时走弧线，反向旋转时原地转向。

## 功能与验收方法

| 功能 | 操作和预期结果 |
| --- | --- |
| 电脑键盘与摇杆 | 按住方向键持续行驶，同时按前后方向与转向键走弧线。圆形摇杆用偏移控制转向和力度。检查前进、倒车时向左和向右四种组合，松手停车 |
| 双手驾驶 | 同时压住油门和转向。只松转向应回正，松油门应停车。离开页面或失去焦点应结束驾驶 |
| 普通与急速 | 停车、双手松开并结束录制后换档。小输入保留细调；满输入时手机直连两种模式分别达到 60% 和 90% PWM。台架点动为 30% |
| 驾驶台显示 | 显示输入比例、前进/空挡/倒车和预计轨迹。油门改变路面动效，转向改变弯道。界面显示的是操控输入，未安装轮速或位置传感器 |
| 录制与重演 | 录制两轴输入和相对时间，保存在当前浏览器。重演时按原时间发送，可从表演页中止。电脑端还可编辑并保存 JSON 路线 |
| 预设和计时 | 蛇形、8 字、组合秀按给定时序运行。绕桩挑战手动开始和结束计时，最好成绩保存在浏览器 |
| 原路返回与定点环绕 | 已有近似返回和定时圆弧。实车效果未达预期，按项目决定保留现状。两项都依靠输入和时序，无操作者定位或位置反馈 |
| 语音扩展 | 提议用第二块 BearPi 接收识别 ID 并复用车端无线接口；首先验收停车和五种基本口令，再考虑车载拾音 |

## 非功能设计

- **停车和失联保护。** 固件上电先关 PWM。相反方向切换预留约 100 ms 停车间隔。连续控制约 700 ms 未刷新时，电机任务主动停车。无线会话在后续请求到达时检查约 600 ms 的有效期，两种超时作用不同。
- **操控响应。** 键盘约 10 ms 检查一次，手机约 100 ms 发送一次持续驾驶请求。实际触摸至车轮响应还包含浏览器、无线传输和机械起动耗时，应以实测报告延迟。
- **多端使用。** 同时只允许一个无线驾驶会话，拒绝错误会话和旧序号。串口调试与无线驾驶分时进行。加入语音后也须处理控制来源冲突。
- **屏幕适配。** 横屏将油门和转向放在两侧，竖屏重新排列。尊重系统减弱动态效果设置，停车后停止道路动画，渲染与发命令各自计时。
- **离线与维护。** 网页资源编入固件，驾驶不依赖校园网和云平台。版本查询、构建哈希、串口启动标记及离线测试帮助排查源码、网页和板端版本不一致。
- **验收条件。** 在相同地面、相近电池电量下比较两种速度和重复路线，记录起点、终点偏差以及停止距离。占空比不直接代表车速；目前没有测得的最高速度、定位精度或语音识别率。
